## 自动生成代码识别规则

### Decision: 采用多重识别策略

**Rationale**: 单一规则无法覆盖所有场景，需要结合路径模式和文件内容标记

### 识别规则集

#### 1. 路径模式排除

```text
# 前端排除路径
frontend/packages/arch/idl/src/auto-generated/**
**/node_modules/**
**/dist/**
**/build/**
**/.next/**
**/__generated__/**

# 后端排除路径
backend/**/generated/**
backend/**/mock/**
```

#### 2. 文件内容标记检测

```text
# 文件头部包含以下标记的应排除
"DO NOT EDIT"
"auto-generated"
"autogenerated"
"Code generated"
"This file is auto-generated"
"Generated by"
```

#### 3. 特殊文件类型排除

```text
# 配置和元数据文件（通常不需要代码注释）
*.d.ts          # TypeScript 类型声明文件（除非是手写的）
*.min.js        # 压缩文件
*.map           # Source map 文件
```

**Alternatives Considered**:
- 仅使用路径模式：不够精确，会遗漏新增的自动生成目录
- 仅使用文件标记：需要读取每个文件，效率较低

## 已有中文注释风格分析

### 后端 Go 代码注释风格

**示例来源**: `backend/domain/workflow/entity/workflow.go`

```go
// Package entity 定义了工作流领域的核心实体
//
// 工作流实体采用了组合模式，通过嵌入多个VO(Value Object)来构建完整的实体：
// - Meta: 工作流的元数据信息（创建者、空间、类型等）
// - CanvasInfo: 画布相关信息
// - DraftMeta: 草稿版本的元数据
// - VersionMeta: 发布版本的元数据
//
// 这种设计的好处：
// 1. 职责分离：不同VO负责不同层次的数据
// 2. 组合灵活：可以根据需要组合不同的VO
// 3. 复用性：VO可以在不同上下文中复用
// 4. 可维护性：每个VO职责单一，易于维护
package entity
```

**Decision**: 采用结构化的多行注释风格

**Rationale**:
- 包级别注释说明整体职责
- 使用列表格式说明组成部分
- 说明设计决策和好处

### 前端 TypeScript 注释风格

**示例来源**: 项目中的 CSS/Less 文件和 TypeScript 文件

```typescript
// 开源版本，如果选择来自 Coze.cn 插件，设置 pluginSource 为 1
if (IS_OPEN_SOURCE) {
  result.data.inputs.pluginFrom = plugin_from;
}
```

**Decision**: 采用行内注释 + JSDoc 风格

**Rationale**:
- 行内注释用于解释业务逻辑
- JSDoc 用于函数和组件的完整文档

## 注释模板标准

### Decision: 建立分层注释模板

#### 文件级别注释（Go）

```go
// Package [name] [简要描述]
//
// [详细描述，包括：]
// - 主要职责
// - 核心概念
// - 与其他包的关系
//
// 使用示例：
//   [简单示例代码]
package name
```

#### 文件级别注释（TypeScript）

```typescript
/**
 * @fileoverview [文件功能简述]
 * 
 * [详细描述，包括：]
 * - 主要功能
 * - 导出的主要接口
 * - 使用场景
 * 
 * @module [模块名]
 */
```

#### 函数/方法注释（Go）

```go
// [函数名] [简要描述]
//
// [详细描述（可选）]
//
// 参数：
//   - [param1]: [参数说明]
//   - [param2]: [参数说明]
//
// 返回值：
//   - [返回值说明]
//
// 注意事项：
//   - [特殊注意点]
func FunctionName(param1, param2 Type) ReturnType
```

#### 函数/组件注释（TypeScript/React）

```typescript
/**
 * [函数/组件简述]
 * 
 * [详细描述（可选）]
 * 
 * @param [param1] - [参数说明]
 * @param [param2] - [参数说明]
 * @returns [返回值说明]
 * 
 * @example
 * ```tsx
 * <ComponentName prop1="value" />
 * ```
 */
```

## 实施批次划分

### Decision: 按优先级和模块分批实施

**Rationale**: 项目规模大（~10,000 文件），需要分阶段实施以保证质量

### 批次规划

| 批次 | 范围 | 预估文件数 | 优先级 |
|------|------|-----------|--------|
| Batch 1 | 后端 domain 层核心实体 | ~100 | P1 |
| Batch 2 | 后端 application 层服务 | ~80 | P1 |
| Batch 3 | 前端 workflow 核心模块 | ~200 | P1 |
| Batch 4 | 前端 agent-ide 模块 | ~150 | P1 |
| Batch 5 | 后端 api 层处理器 | ~60 | P2 |
| Batch 6 | 后端 infra 基础设施层 | ~80 | P2 |
| Batch 7 | 前端 arch 基础架构包 | ~150 | P2 |
| Batch 8 | 前端 common 共享组件 | ~200 | P2 |
| Batch 9 | 前端其他功能模块 | ~500 | P3 |
| Batch 10 | 配置文件和脚本 | ~50 | P3 |

**Alternatives Considered**:
- 按文件字母顺序：不考虑业务重要性
- 一次性全部添加：风险太高，难以保证质量

## 质量保证策略

### Decision: 采用抽样检查 + 自动化验证

**Rationale**: 完全人工检查不现实，需要自动化辅助

### 质量验证方法

1. **注释存在性检查**
   - 脚本检测文件是否包含中文字符
   - 检测公共函数是否有 JSDoc/Go doc

2. **注释准确性检查**
   - 每批次完成后抽样 10% 文件人工验证
   - 重点检查注释与代码是否一致

3. **格式规范检查**
   - ESLint 规则验证 JSDoc 格式
   - Go lint 验证注释格式

## 工具和依赖

### 无需额外依赖

**Decision**: 使用现有工具链

**Rationale**:
- 注释添加是人工/AI 辅助的文本编辑工作
- 现有 ESLint 和 Go lint 已可验证注释格式
- 不需要引入新的构建或运行时依赖

### 辅助脚本需求

```bash
# 统计注释覆盖率
find . -name "*.go" -exec grep -l "[\u4e00-\u9fff]" {} \; | wc -l

# 检测自动生成文件
grep -rn "DO NOT EDIT\|auto-generated" --include="*.go" --include="*.ts"
```

## 风险和缓解措施

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 注释与代码不一致 | 误导开发者 | 定期复查 + CI 检查 |
| 过度注释降低可读性 | 代码臃肿 | 只注释复杂逻辑，不注释显而易见的代码 |
| 注释风格不统一 | 混乱 | 提供模板 + 示例 |
| 自动生成代码误添加注释 | 被覆盖 | 严格执行排除规则 |
